## 2. Numbers verified by hand, with derivations

**The slack between `statsGlobs` and `textGlobs` is 4 bytes, not 8.** Prior sessions recorded 8.

```
statsGlobs                  0x00503bd8 + 0x5b0 = 0x00504188   Stats.cpp:41, Stats.h:232
g_Teleporter_BOOL_00504188  0x00504188, 4 bytes               Teleporter.cpp:17
textGlobs                   0x00504190                        TextMessages.cpp:24
raw gap 8 − 4 occupied = 4 FREE
```

Raising `LegoObject_ID_Count` 15→16 adds `20 × 4 = 80` bytes to `Stats_Globs`, so it does not
merely run 72 bytes into `Text_Globs` — it **destroys a live Teleporter flag first**. Same
conclusion, better evidence. Pinned by `test_scalar_inside_gap_is_counted`.

**A 16th monster ID aliases the Tool Store.** In a `[20][15]` table the linear index of
`[3][15]` is `3*15 + 15 = 60`, which is `[4][0]`. `LegoObject_Building == 4`
(`GameCommon.h:1075`). So an ID-15 RockMonster silently reads and writes **Building ID 0's
row** — the Tool Store in stock data. No crash, no warning, no `assert_sizeof` trip; just a
Tool Store whose stats drift as monsters spawn.

**There is no hook trampoline.** `hook_write_jmpret` overwrites a function prologue with
`E9 rel32` + `C3` and every restore path in `hook.cpp:30-32,47-49` is commented out. Counted
across the tree: **1515 hook installations, zero passing a backup buffer.** There is no way to
call an original implementation, so any re-implementation must be complete, never a wrapper.

**44 warnings is real, not incremental noise.** An incremental build shows only recompiled
files (25 at one point), which is why every claim here comes from `-t:Rebuild`.

## 3. Judgement calls made against the obvious path

**Tier 3 — raising the ID ceiling — was abandoned, on evidence.** The mandate said to take the
more exceptional path; it also said to skip anything provably a dead end. This is the latter.
A DLL-side mirror only works if *every* toucher of a table is C++. Of the six tables a monster
ID reaches, three are ours, but `Dependencies` (0 of 11 implemented), `Interface` (3 of 99) and
`AITask` (9 of 105) are not — and they are fed by `Lego_GetObjectByName`, exe code with seven
exe callers. You cannot mirror a table whose writer is 1999 machine code, and there is no safe
index to hand those consumers because every index ≥ 15 aliases Building 0. Price of a usable
ID 15: **~200 exe functions**. That is decompilation work, not design work.
Full reasoning: `docs/research/type-loader-reimplementation.md` §4.

**Reimplementing `Lego_LoadRockMonsterTypes` was also rejected.** It unlocks nothing — the free
ID slots below 15 already work with no code at all, because both consumers are count-driven —
while carrying the one risk this project cannot absorb: an unverifiable behavioural regression
in startup code, with no trampoline to fall back to. Every gain attributed to it (validation,
loud errors, a load-time hook) was built instead in C++ we already own.

**The three correctness fixes are unconditional, not gated.** Gating exists so a player can
turn one thing on and know what broke. That logic does not apply when the behaviour being
replaced is memory corruption: there is no vanilla semantics worth preserving, and any config
reaching those paths is already broken.

**They complain *and* skip.** Fatal-error visibility is a runtime-toggleable log level
(`Errors.h`), so a message alone would not prevent the write. The `continue` is what actually
guarantees it.

**On the slug fix, I took half of what the analysis recommended.** It suggested also calling
`Level_Block_SetBusy(&blockPos, true)`. I set `targetBlockPos` but did not add the busy flag,
because the only code that *clears* it is the same branch whose reachability is unproven —
setting it could strand a block permanently busy and make Rock Raiders refuse to work it for
the rest of the mission. That trades a possibly-unreachable corruption for a definitely-real
gameplay regression. Defensive fix yes; speculative behaviour change on an unverifiable path, no.

**Water was left as graceful degradation pending the real relocation.** See §5.

## 4. Provisional and unverified — read this before trusting anything

- **Nothing here has been run.** Not once. Every feature, every fix.
- `LegoObject_IsRockMonsterCanGather` is an exe macro (`Object.cpp:5186`), so whether the
  `targetBlockPos` corruption is actually *reachable* for slugs is **unknown**. The fix is
  inert if not, correct if so.
- The species pool and variant/beam tables are **empty by default**, because the names that
  exist live in the user's own `Lego.cfg`, which this project has never read. Unresolvable
  names are reported and skipped rather than guessed.
- `addrlint` lists **1 binding whose size it cannot derive**; it is excluded from overlap
  maths. The map is incomplete by exactly that much, deliberately — guessing a size would
  produce false confidence, which is worse than a visible gap.
- The linter's sizes come from the source's own `assert_sizeof`, not from a compiler. They are
  `static_assert`s, so a *wrong* one fails the build — but a *missing* one leaves a hole.
- `docs/research/*.md` were produced by analysis agents. Their headline claims were re-derived
  by hand before anything was built on them; their secondary claims were not. In a prior
  session adversarial verification refuted most unchecked headline claims, so treat anything in
  those documents that is not repeated in this handoff as **provisional**.

## 5. Where I would start tomorrow

1. **Finish the water relocation.** `docs/research/water-relocation.md` is a complete
   implementation design and its verdict is that full DLL-side relocation is safe today, with
   one small blocker (`Water_FindPoolDrain` is the only place a `Water_Pool*` escapes the
   module). The key move is replacing `Water_Pool*` with `uint32` indices throughout, and
   `std::unique_ptr` storage for pointer stability. Acceptance test is exact: `addrlint` must
   still report 113 regions and 0 overlaps, and `docs/ADDRESS-MAP.md` must not change.
2. **The wave director.** `docs/research/wave-director.md` has the spawn recipe, the block-flag
   semantics, the object-iterator idiom, the hook slot, and four *implemented* telegraphing
   channels (`Info_Send`, `SFX_Random_PlaySoundNormal`, `Camera_Shake`, `Smoke_CreateSmokeArea`).
3. **Work down `docs/research/silent-failures.md`.** F-01 is fixed; F-02 through F-12 are ranked
   and unfixed. Several are `strcpy`-into-fixed-buffer and uncapped-counter overflows in
   `Priorities.cpp`, `SFX.cpp` and `Config.cpp`. Note F-04: an `sfxGlobs` overflow runs directly
   into `statsGlobs` — independently confirmed by `ADDRESS-MAP.md`, where `sfxGlobs` ends at
   exactly `0x00503bd8`, the address `statsGlobs` begins at.
4. **Total stats overhaul** — 57 numeric knobs × 71 ability flags across 11 species. Pure data,
   no engine risk, and the largest untapped source of felt variety.

## 6. The single highest-value experiment for anyone who has the game installed

**Does the exe's `RockMonsterTypes` loader accept a name it has never seen?**

Add a 12th entry to the `RockMonsterTypes` block in `Lego.cfg` (loose files override the WADs)
and see whether `Lego_GetObjectByName` resolves it. That one test gates the entire roster
question. It fails **silently** — `Stats_Initialise` warns and `continue`s on an unresolved
name — so watch the log rather than the screen.

Second most valuable: run any mission at all with `VerboseStartup TRUE` and confirm
`Settings\DeepCore.cfg` is found and parsed. Nothing in this fork has ever been observed
loading.
