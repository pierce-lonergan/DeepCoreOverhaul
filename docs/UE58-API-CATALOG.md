## How to use this document

Every API listed here was opened in the local 5.8 source and confirmed by a second adversarial pass. Where the first pass was wrong, the correction is what appears below — the original claim is gone, not softened. Anything that could not be confirmed is in **Unverified — check before relying on**, and anything nobody looked at is in **Not yet investigated**.

Paths are relative to `C:\Program Files\Epic Games\UE_5.8\Engine\`. A path beginning `Source/` means `Engine/Source/`; `Plugins/`, `Content/` and `Config/` are likewise under `Engine/`.

**Availability** is the load-bearing column. It answers "can DeepCore actually use this":

| Label | Meaning |
|---|---|
| `RUNTIME` | Fully constructible and drivable from C++ at runtime. No asset. Works in a cooked Game build. |
| `ENGINE_ASSET` | Needs an asset, but one already ships in `/Engine`. Free — **but you must force it into the cook** (see §H). |
| `EDITOR_ONLY` | Requires an authored asset or an editor-only code path. Effectively unavailable. |
| `NOT_LINKABLE` | The symbol exists and is correct, but lives in a `Private` header or a Developer/Editor module. Reference only — you cannot call it from the `DeepCore` module. |
| `UNCLEAR` | Genuinely ambiguous. Stated as such rather than guessed. |

**Maturity** is taken from the `.uplugin` manifest or an explicit source marker, never from recollection. Beta and Experimental are labelled every time they appear and are never presented as stable.

Read **Start here** and **Silent no-ops and traps** even if you read nothing else. The project has twice lost time to APIs that compiled, ran, logged nothing, and did nothing.

## The two hard constraints

**1. Zero content assets.** No `.uasset` of the project's own. No meshes, textures, materials, maps. The startup map is `/Engine/Maps/Entry.Entry` and everything visible is spawned by `ADeepCoreGameMode::BeginPlay`. Any API whose only driver is an editor-authored asset is unavailable, regardless of how attractive it looks.

This constraint is *stronger* than it first appears, because it removes several whole engine subsystems by transitivity: no material graphs → no Custom Primitive Data, no per-instance custom data, no runtime virtual textures, no post-process materials, no light functions, no Niagara. Those are not separate limitations; they are one limitation seen from six angles.

**2. No LEGO Rock Raiders, and no other commercial game's assets, data, or code.** Ever, in any form, including "just for reference" or "to convert". Everything is original or generated. No route in this document involves extracting, converting, or importing another game's content, and none may be added.

## Start here — the decisions on the table right now

### 1. Runtime geometry: migrate settled geometry to runtime-built `UStaticMesh`. Keep `UDynamicMeshComponent` for the dig face. **Never use HISM.**

This leads because it determines whether Lumen ever works.

`FPrimitiveSceneProxy::UpdateVisibleInLumenScene` (`Source/Runtime/Engine/Private/PrimitiveSceneProxy.cpp:1691`) has two branches. The software branch requires `DoesProjectSupportDistanceFields() && AffectsDistanceFieldLighting() && (SupportsDistanceFieldRepresentation() || SupportsHeightfieldRepresentation())`. **No runtime-constructible geometry in UE 5.8 can satisfy it** — mesh distance fields are built under `WITH_EDITORONLY_DATA` and `r.GenerateMeshDistanceFields` is `ECVF_ReadOnly` (`Source/Runtime/Engine/Private/DistanceFieldAtlas.cpp:59`). `UDynamicMeshComponent` does not rescue this: its proxy hardcodes `bWillHaveDistanceField = false` (`Source/Runtime/GeometryFramework/Private/Components/BaseDynamicMeshSceneProxy.cpp:66`) and `SetNewDistanceField` does `ensureMsgf(false, "Distance fields not supported")` (`:869`).

So `r.Lumen.HardwareRayTracing=1` is not a quality setting. It is the only branch on which this game's geometry receives GI at all. That finding, already in `DefaultEngine.ini`, is re-confirmed in 5.8 source and must not be relaxed.

What migration actually buys, then, is everything *except* distance fields: static relevance, cached mesh draw commands, GPUScene participation (`FStaticMeshSceneProxy` is the only one of these proxies that calls `EnableGPUSceneSupportFlags()` — `Source/Runtime/Engine/Private/StaticMeshSceneProxy.cpp:432`), LOD slots, and an uncullable ray-tracing proxy. Against that, `UProceduralMeshComponent` is dynamic-relevance-only, binds a per-draw primitive uniform buffer, retains a double-precision CPU vertex copy per section forever, and does a **full BLAS rebuild on every `UpdateMeshSection`** (initializer is `bFastBuild=true, bAllowUpdate=false` — `Plugins/Runtime/ProceduralMeshComponent/Source/ProceduralMeshComponent/Private/ProceduralMeshComponent.cpp:166-168`, rebuild at `:271-288`). For a game whose core verb is "change the geometry", that last point is the dominant hidden cost.

Pipeline: `FDynamicMesh3` (built on a worker from `GeometryCore` generators) → `FDynamicMeshToMeshDescription::Convert` → `UStaticMesh::BuildFromMeshDescriptions` with `bFastBuild=true` → `UStaticMeshComponent` per chunk, `UInstancedStaticMeshComponent` per repeated brick.

**`UHierarchicalInstancedStaticMeshComponent` is a correctness dead end, not a performance trade-off.** `Source/Runtime/Engine/Private/HierarchicalInstancedStaticMesh.cpp:807` sets `bVisibleInLumenScene = false;` with the comment *"Dynamic draw path without Nanite isn't supported by Lumen"*. The base `FStaticMeshSceneProxy` constructor calls `UpdateVisibleInLumenScene()` first (`StaticMeshSceneProxy.cpp:481`); the HISM constructor body then overwrites it — derived body runs last, false wins. DeepCore has no Nanite path and never will, so a HISM contributes zero GI regardless of any cvar. Line `:813` is also the only place in the entire engine that sets `bDynamicRayTracingInstances = true`, which makes HISM simultaneously the one component that *does* get angle-culled out of the TLAS.

Plain `UInstancedStaticMeshComponent` is fine and is **not** angle-culled — see §A for why the widely-repeated `CullAngle` warning does not apply.

### 2. Add a fail-loud RHI capability gate to `BeginPlay`, before any geometry spawns.

`FProceduralMeshSceneProxy` creates its `FRayTracingGeometry` only inside `if (IsRayTracingEnabled())`, evaluated once at proxy-construction time (`ProceduralMeshComponent.cpp:157-180`, inside `#if RHI_RAYTRACING`). If ray tracing is not enabled when the terrain spawns, the geometry never enters the TLAS, never receives Lumen GI, and **nothing warns you** — the entire mine renders unlit.

This is exactly the documented past failure (SM6 targeted in ini, SM5 silently running, every RT cvar reading back `1`). It is directly self-detectable:

```cpp
void ADeepCoreGameMode::VerifyRenderingCapabilities()
{
    const bool bSM6  = (GMaxRHIFeatureLevel == ERHIFeatureLevel::SM6);
    const bool bHW   = GRHISupportsRayTracing;      // #include "RHIGlobals.h"
    const bool bRTOn = IsRayTracingEnabled();       // RenderCore
    UE_LOG(LogDeepCore, Display, TEXT("FeatureLevel=%d SM6=%d HWRT=%d RTEnabled=%d"),
           (int32)GMaxRHIFeatureLevel, bSM6, bHW, bRTOn);
    if (!bSM6 || !bHW || !bRTOn)
    {
        UE_LOG(LogDeepCore, Fatal,
            TEXT("DeepCore requires SM6 + hardware ray tracing: procedural geometry is invisible ")
            TEXT("to software Lumen. Check +D3D12TargetedShaderFormats=PCD3D_SM6 / -PCD3D_SM5."));
    }
}
```

Fifteen lines. Requires adding `"RenderCore"` and `"RHI"` to `DeepCore.Build.cs` (see §I). `GMaxRHIFeatureLevel` cannot read back a misleading `1` the way the RT cvars can.

### 3. Set `ShadowCacheInvalidationBehavior = Rigid` on every PMC before `RegisterComponent()`. **Never `Static`.**

`UPrimitiveComponent` defaults this to `Auto` (`Source/Runtime/Engine/Classes/Components/PrimitiveComponent.h:372`, default set at `Private/Components/PrimitiveComponent.cpp:347`). `FPrimitiveSceneProxy` defaults `bHasDeformableMesh(true)` "to be conservative" (`PrimitiveSceneProxy.cpp:386`) and PMC never clears it. `FVirtualShadowMapPerLightCacheEntry::OnPrimitiveRendered` (`Source/Runtime/Renderer/Private/VirtualShadowMaps/VirtualShadowMapCacheManager.cpp:1288-1291`) therefore issues an unconditional invalidation for every procedural primitive, in every local light's VSM, every frame. `r.Shadow.Virtual.Cache=1` is currently doing nothing for the entire scene.

`Rigid` takes the proxy out of that branch. **`Static` is unsafe here**: the cache manager early-returns on `EInvalidationCause::Updated` when the behavior is `Static` (`VirtualShadowMapCacheManager.cpp:571-576`), and `UProceduralMeshComponent::UpdateMeshSection*` does an in-place render-thread vertex-buffer update and then calls only `MarkRenderTransformDirty()` — never `MarkRenderStateDirty`, never recreates the proxy (`ProceduralMeshComponent.cpp:745-761`). Under `Static`, any dig implemented via `UpdateMeshSection` leaves permanently stale shadows.

The value is snapshotted into the proxy at construction (`Source/Runtime/Engine/Private/PrimitiveSceneProxyDesc.cpp:177`), so it must be set before registration.

### 4. Materials: two engine parents, and add the cook directives now.

You cannot author a `UMaterial` in a cooked build. `FMaterial::CacheShaders` only reaches `BeginCompileShaderMap` inside `#if WITH_EDITORONLY_DATA` (`Source/Runtime/Engine/Private/Materials/MaterialShared.cpp:3213/3219`), and on failure it does `SetGameThreadShaderMap(nullptr)` and renders as the default material — silently. `UMaterialExpression` is `UCLASS(abstract, Optional, ...)`, i.e. harvested out of cooked packages (`Source/Runtime/CoreUObject/Private/UObject/SavePackage/PackageHarvester.cpp:503`).

`DeepCoreMaterials.cpp` already handles this correctly: the graph builder is inside `#if WITH_EDITOR` (guard opens `:9`/`:25`, closes `:334`) with a non-editor fallback that loads `/Engine/EngineDebugMaterials/VertexColorMaterial`. **Do not "clean that up".** It means DeepCore is *not* editor-linked, which in turn closes the tempting full-`UStaticMesh::Build()` route to runtime distance fields — that route would permanently tie the project to an editor-linked target.

Recommended parents:
- **Bricks / units / props:** `/Engine/EngineDebugMaterials/VertexColorMaterial` — `MD_Surface`, `BLEND_Opaque`, `MSM_DefaultLit`, `VertexColor → BaseColor` via `ConvertFromDiffSpec`. Zero parameters, so all variation goes through the vertex buffer — which is exactly right for thousands of independently-tinted bricks at zero per-brick cost.
- **Rock walls:** `/Engine/EngineDebugMaterials/VertexPaint_4Tex` — lit, four `TextureSampleParameter2D` diffuse slots plus four normals, blended by full vertex RGBA. Strictly better than the two-way `VertexPaint_2Tex_Color` alpha lerp for layered strata, at the same cost, from the same directory. Feed it `UTexture2D::CreateTransient` noise/normal maps through a MID.

Then, in `Config/DefaultGame.ini`:
```ini
[/Script/UnrealEd.ProjectPackagingSettings]
+DirectoriesToAlwaysCook=(Path="/Engine/EngineDebugMaterials")
+DirectoriesToAlwaysCook=(Path="/Engine/Engine_MI_Shaders")
```
The section name is still `/Script/UnrealEd....` despite the class moving to `DeveloperToolSettings` — there is a `ClassRedirect` at `Config/BaseEngine.ini:960`. The cooker follows *asset references*; a C++ string literal is not one. Without this the packaged game boots to `WorldGridMaterial`.

### 5. Destruction: `UClusterUnionComponent` + analytic box bodies + ISM. Not geometry collections.

The geometry-collection *simulation* half is genuinely runtime-constructible (see §D). The *rendering* half is not: `FGeometryCollectionRenderData::Create` is both `#if WITH_EDITOR` and in a `Private` header (`Source/Runtime/Experimental/GeometryCollectionEngine/Private/GeometryCollection/GeometryCollectionRenderData.h:135`), so `RenderData` is permanently null and `CreateSceneProxy` returns nullptr (`GeometryCollectionComponent.cpp:1149`). A runtime-built collection simulates perfectly and draws nothing.

The brick-native path avoids that entirely, and avoids the PMC collision re-cook: a `UBodySetup` carrying only `FKBoxElem` with `bNeverNeedsCookedCollisionData = true` makes `UBodySetup::CreatePhysicsMeshes()` return immediately (`Source/Runtime/Engine/Private/PhysicsEngine/BodySetup.cpp:428-429`) — no Chaos cook anywhere in the dig loop. `UShapeComponent` does exactly this (`Private/Components/ShapeComponent.cpp:251`), so it is a first-class supported path.

Keep the geometry-collection pipeline in reserve for one thing it does better than anything else: large scripted cave-ins with real strain propagation via `ApplyExternalStrain` + `SetAnchoredByBox`. Prove a custom `IGeometryCollectionExternalRenderInterface` first, or it is invisible.

### 6. Pathing: `FGraphAStar` over the tile grid. Do not spawn a navmesh.

Recast is structurally wrong for a game whose core verb changes the geometry. At the real defaults — `TileSizeUU=1000` (`Config/BaseEngine.ini:3052`) over `CellSize=19` (`:3053`, **not** the 25 struct default) — one tile is ~53×53 voxel columns, and a one-voxel change rebuilds the whole tile through rasterize → filter → compact → watershed partition → contour → poly mesh → detail mesh. Dirty areas also expand by one `AgentRadius` (`RecastNavMeshGenerator.cpp:1804-1811`), so a dig near a boundary dirties neighbours.

Worse, nothing dirties it for you: `ProceduralMeshComponent.cpp` contains **zero** navigation symbols, and `UPrimitiveComponent`'s constructor sets `bCanEverAffectNavigation = false` (`PrimitiveComponent.cpp:401`). `UpdateMeshSection` reaches neither of `USceneComponent`'s two automatic nav-refresh sites (`SceneComponent.cpp:698` on registration, `:1038-1040` inside `PropagateTransformUpdate`).

Since the world is already a grid, `FGraphAStar` is both faster and *more correct* — a dig is an O(1) cost-array write and connectivity is exact rather than voxel-approximated, which eliminates the entire "navmesh says walkable, geometry says wall" bug class.

### 7. Audio: build every sound as a runtime MetaSound graph — and supply your own attenuation.

The MetaSound Builder API is the single best thing available to this project: fully runtime, non-beta, plugin already enabled by default, zero assets, and it turns the project's biggest liability into a non-issue for an entire discipline. See §F.

But two silent failures sit directly on the recommended path. `UGameplayStatics::SpawnSoundAtLocation` takes a `USoundAttenuation*` **asset** (`Source/Runtime/Engine/Classes/Kismet/GameplayStatics.h:754`), and a builder-produced transient `UMetaSoundSource` has `AttenuationSettings == nullptr` — so it plays fully 2D with no falloff, no occlusion, no reverb send. And `Audition()` (`Plugins/Runtime/Metasound/Source/MetasoundEngine/Private/MetasoundBuilderSubsystem.cpp:143-181`) configures nothing but `SetSound` + `Play`. Configure the `UAudioComponent` — including `bOverrideAttenuation = true` — *before* calling `Audition`, or `NewObject<USoundAttenuation>()` (it is concrete and asset-free: `Source/Runtime/Engine/Classes/Sound/SoundAttenuation.h:451`).

### 8. Enhanced Input is currently inert. Five lines fix it.

`"EnhancedInput"` is in `DeepCore.Build.cs`, but `UInputSettings`' compiled-in defaults are `UPlayerInput` and `UInputComponent` (`Source/Runtime/Engine/Private/UserInterface/InputSettings.cpp:52-53`), and the project ships **no `Config/DefaultInput.ini` at all**. Every `AddMappingContext` / `BindAction` call would no-op.

```cpp
ADeepCorePlayerController::ADeepCorePlayerController()
{
    OverridePlayerInputClass = UEnhancedPlayerInput::StaticClass();
}
void ADeepCorePlayerController::SetupInputComponent()
{
    if (InputComponent == nullptr)
    {
        InputComponent = NewObject<UEnhancedInputComponent>(this, TEXT("PC_InputComponent0"));
        InputComponent->RegisterComponent();
    }
    Super::SetupInputComponent();
}
```
`PlayerController.cpp:2649` explicitly comments that a subclass may do this. Prefer the C++ route over the ini route so the truth lives next to the bindings. Then `NewObject` the `UInputAction`s and `UInputMappingContext` and wire them with `UInputMappingContext::MapKey` — both classes are plain `UDataAsset` subclasses with public runtime APIs.

### 9. Fix determinism now, before saves and tests exist.

Three separate existing recommendations silently assume reproducible generation: seed+delta saves, "same seed → byte-identical output" automation tests, and the tuning-sweep workflow. Nothing has specified how. `FMath::Rand()`/`FMath::FRand()` are global-state and are *actively wrong* on the worker tasks the geometry pipeline recommends.

Establish the rule today: **one `FRandomStream` per chunk, seeded from `HashCombine(WorldSeed, ChunkCoord)`, never shared across parallel work.** `Source/Runtime/Core/Public/Math/RandomStream.h:19` (`Initialize(int32)` `:63`, `Initialize(FName)` `:75`, `GetFraction()` `:115`). Separately decide whether saves must be portable across compilers/platforms — floating-point noise is not guaranteed bit-identical, and that decision constrains the save format.

### 10. LOD: `SignificanceManager` is the only engine answer left standing.

Every automatic LOD system is closed here: no Nanite (runtime geometry cannot have it), no mesh distance fields, no HLOD (needs cooked proxies), no World Partition (needs actor descriptors, which spawned actors do not have). `USignificanceManager` works entirely on runtime C++ objects with zero assets and is the cheap middle step that usually removes the need to migrate units to Mass at all. It is in **Not yet investigated** because no leg surveyed it — it should be the first thing investigated.

### Notes

**Module dependencies are simpler than they look.** `GeometryFramework.Build.cs` already lists `GeometryCore`, `MeshConversion`, `MeshDescription`, `StaticMeshDescription` (and `SkeletalMeshDescription`, `InteractiveToolsFramework`) in `PublicDependencyModuleNames`. Adding `"GeometryFramework"` alone supplies all five. All are `Engine/Source/Runtime` modules — **no `.uproject` plugin change**. `ProceduralMeshComponent` also brings `RenderCore`, `RHI`, `MeshDescription`, `StaticMeshDescription`, `PhysicsCore` publicly, so several dependencies you might add are already transitively present.

**The ISM ray-tracing cull warning you will find online does not apply to plain ISM in 5.8.** `FInstancedStaticMeshSceneProxy::GetDynamicRayTracingInstances` (`Source/Runtime/Engine/Private/InstancedStaticMesh.cpp:1842`) opens with `if (!bDynamicRayTracingInstances && !bDynamicRayTracingGeometry) { return; }` at `:1847`. `FStaticMeshSceneProxy`'s constructor sets both false (`StaticMeshSceneProxy.cpp:381-382`); `bDynamicRayTracingGeometry` only becomes true for WPO materials with `bEvaluateWorldPositionOffsetInRayTracing`, and `r.RayTracing.Geometry.InstancedStaticMeshes.EvaluateWPO` defaults to 0 (`InstancedStaticMesh.cpp:155`). Nothing in the tree sets `bDynamicRayTracingInstances = true` for a plain ISM. A default ISM is ray-tracing-*static*-relevant (`IsRayTracingStaticRelevant`, `StaticMeshSceneProxy.h:182-187`) and enters the TLAS via `GetStaticRayTracingInstances` (`StaticMeshSceneProxy.cpp:2088`), which contains no `CullAngle` / `CullClusterRadius` / `LowScaleCullRadius` logic at all. The angle-cull code at `InstancedStaticMesh.cpp:2072-2093` is unreachable. **Do not set `r.RayTracing.Geometry.InstancedStaticMeshes.Culling=0`** — it buys nothing.

The general lesson, worth internalising: `FPrimitiveSceneProxy` exposes *both* `GetStaticRayTracingInstances` and `GetDynamicRayTracingInstances` (`StaticMeshSceneProxy.h:177-179`), and `IsRayTracingStaticRelevant()` picks. Any future "is this thing in the TLAS" analysis must check that first, or it will read the behaviour of a path the component never enters.

**`bAllowCpuAccess` needs two writes, not one.** `Params.bAllowCpuAccess` is only OR'd into the index-buffer flag (`StaticMesh.cpp:8977`); it never writes the `UStaticMesh::bAllowCPUAccess` member (`StaticMesh.h:1423`). The non-editor guard in `GetPhysicsTriMeshDataCheckComplex` (`:9272`) tests the *member*. Set both, or runtime tri-mesh collision works in the editor and silently fails in a cooked build:
```cpp
SM->bAllowCPUAccess = true;
P.bAllowCpuAccess    = true;
```
Also note `BuildFromMeshDescriptions` asserts `check(Params.bCommitMeshDescription || Params.bFastBuild)` at `StaticMesh.cpp:8933` — both false is a hard check failure, not a fallback. And `FStaticMeshAttributes(MD).Register()` must be called before filling, or the build produces garbage.

**`UDynamicMeshComponent` static draw path is editor-shaped.** `SetMeshDrawPath(StaticDraw)` gives cached draw commands, but `AllowFastUpdate()` then returns false — every `FastNotify*` falls back to a full proxy recreate. Do not enable it on meshes you edit. Its relevance-flip escape hatches are also compiled out of Shipping/Test: `BaseDynamicMeshSceneProxy.cpp:531-535` does `if (!AllowDebugViewmodes()) { return true; }` *before* the wireframe/collision/ColorMode checks, so a DMC in `StaticDraw` behaves differently in the editor than in a shipped build.

**DMC's Lumen cards are downstream of already being Lumen-visible.** `UpdateLumenCardsFromBounds` (`BaseDynamicMeshSceneProxy.cpp:831`) early-outs on `!bVisibleInLumenScene || !AllowLumenCardGeneration()` (`:833`). Cards cannot rescue a proxy that failed `UpdateVisibleInLumenScene`; they only improve one that passed. Under this project's `LightingMode=1` (hit lighting), they are moot anyway.

**PMC memory.** `FProcMeshVertex` (`ProceduralMeshComponent.h:70`) stores `FVector` Position + `FVector` Normal + `FProcMeshTangent` + `FColor` + 4× `FVector2D`, all double-precision in UE5 — ~150 bytes/vertex, and `ProcMeshSection` keeps that CPU copy alive forever. For a brick world this is a real budget item, and the recommended `UStaticMesh` migration adds a *second* copy (`bAllowCPUAccess` is required for collision). Nobody has computed a per-chunk budget yet; see **Not yet investigated**.

**One more `FStaticMeshSceneProxy` subtlety.** `bSupportsDistanceFieldRepresentation` (`StaticMeshSceneProxy.cpp:340`) requires more than "DistanceFieldData exists" — it also requires `MaterialRelevance.bOpaque && !bUsesSkyMaterial && !bUsesSingleLayerWaterMaterial`. And at `:478-481`, `UpdateVisibleInLumenScene()` is skipped entirely for single-layer-water materials, leaving `bVisibleInLumenScene` at its constructor value. Irrelevant for opaque rock; a landmine if translucent or water-ish materials ever appear in the cave.

### Notes

**MegaLights is a genuine trade-off, not free upside.** Its target case is exactly yours — many small shadow-casting lamps, no directional light — and `r.MegaLights.Volume=1` feeds a stochastically ray-traced light volume straight into volumetric fog (`Engine/Shaders/Private/VolumetricFog.usf`, `USE_MEGA_LIGHTS`), giving shadowed god-rays from every lamp at fixed cost. Its RT shadows trace the same BVH PMC already populates.

The cost: enabling it *removes* lamps from the per-light shadowed fog-injection path. `LightNeedsSeparateInjectionIntoVolumetricFogForOpaqueShadow` (`Source/Runtime/Renderer/Private/VolumetricFog.cpp:731-755`) requires a projected shadow, a static shadow depth map, an allocated VSM id, or RT shadows with `r.VolumetricFog.InjectRaytracedLights`. Under MegaLights at `DefaultShadowMethod=0` a lamp gets none of those, drops out of injection (`:1551-1574`), and its fog contribution comes entirely from the `MegaLightsVolume` texture — whose resolution is governed by `r.MegaLights.Volume.GridPixelSize`/`.GridSizeZ`/`.NumSamplesPerVoxel`, **not** `r.VolumetricFog.GridPixelSize`. For a god-ray-driven art direction, validate beam sharpness against the current look before flipping it on. Also note it is HWRT-or-nothing here: its software fallback is Global SDF, which is dead for this project.

Correction to a widely-repeated claim: turning `r.MegaLights.Volume` off does **not** silence those lamps in fog. `VolumetricFog.cpp:1929` sets `bUseMegaLights = View.GetMegaLightsVolume().Texture != nullptr && MegaLights::IsEnabled(...)`; with no volume texture the permutation is off and the fog light-grid loop covers all lights again. You lose the god-rays, not the lamps.

Note also `FPostProcessSettings`' constructor default for `bMegaLights` is `true` (`Source/Runtime/Engine/Private/Scene.cpp:487`), normally overwritten from the cvar in `FSceneView::StartFinalPostprocessSettings` (`SceneView.cpp:2110-2112`). Any path consuming a raw `FPostProcessSettings` without going through that function — scene captures, custom view families — sees MegaLights on by default.

**Lumen surface cache is permanently unavailable, and that is fine.** `FLumenSceneData::AddMeshCards` (`Source/Runtime/Renderer/Private/Lumen/LumenMeshCards.cpp:887-956`) requires `Proxy->GetMeshCardRepresentation()`; the base returns nullptr (`PrimitiveSceneProxy.h:506`) and PMC does not override it, so the primitive group is flagged `SetHasValidMeshCards(false)` forever. Every `r.LumenScene.SurfaceCache.*` and `r.LumenScene.Radiosity.*` cvar, and `LumenSkylightLeaking`/`LumenSurfaceCacheResolution` in `FPostProcessSettings`, are inert. This is why `LightingMode=1` is mandatory — and it also means secondary bounces (which always sample the surface cache) return black on your walls. **Budget for a one-bounce look**, and compensate with lamp intensity and `LumenDiffuseColorBoost` rather than expecting multi-bounce fill.

Hit lighting can also silently downgrade: `GetHitLightingMode` returns `SurfaceCache` if RayGen shaders are unavailable (`GRHISupportsRayTracingShaders && GRHISupportsRayTracingDispatchIndirect`), or if a scalability profile sets `r.Lumen.HardwareRayTracing.HitLighting.Allowed=0`. Verify `Allowed` is 1 at runtime, not just that `LightingMode` reads 1.

**Bias tuning lives in the VSM cvars, not the light.** `ULightComponent::ShadowBias`/`ShadowSlopeBias`/`ShadowSharpen`/`ShadowResolutionScale` drive conventional shadow-map projection and are effectively inert under VSM. Small-geometry acne on brick-scale meshes is tuned with `r.Shadow.Virtual.NormalBias` (default 0.5), `r.Shadow.Virtual.ScreenRayLength` (0.015) and the `SMRT.*Local` family. This is the most common wasted-effort trap in the domain.

`r.Shadow.Virtual.DistantLightMode` (default 1) is your friend for a cave full of small lamps: lights below a pixel-footprint threshold get force-cached and round-robin updated at `r.Shadow.Virtual.MaxDistantUpdatePerFrame` (default 1). The cost is a one-or-more-frame stale shadow when the player rounds a corner. Also note `r.Shadow.Virtual.ShowStats` is deprecated (5.7) in favour of `r.Shadow.Virtual.Stats.Visible` — older ini snippets silently do nothing.

**Local fog volumes have two silent clamps.** `r.LocalFogVolume.MaxDensityIntoVolumetricFog` defaults to `0.01` — however dense you make a dust cloud, its contribution to the fog grid is clamped to that. And `r.LocalFogVolume.GlobalStartDistance` defaults to `1000` cm; the component's own `FogStartDistance` is clamped to be ≥ it, so a dust cloud within 10 metres of the player is invisible. In a cramped mine that is almost certainly wrong. Outside the fog grid, a local fog volume is shaded only by a directional light + skylight (`LocalFogVolumeRendering.cpp:599-624`) — i.e. by nothing, here. It is *only* useful via `RenderIntoVolumetricFog`.

**Volumetric fog gotchas worth knowing:** volumetric fog does not support `StartDistance`, `FogMaxOpacity` or `FogCutoffDistance` (the header says so). With `r.SupportExpFogMatchesVolumetricFog=1`, several height-fog properties are ignored in favour of the volumetric values. Beam sharpness is dominated by `r.VolumetricFog.GridPixelSize` (16 default; 8 doubles resolution at ~4× cost), not by any component property. And with `HistoryWeight` at 0.9, fast geometry changes from digging will ghost.

**IES profiles: initialise `TextureMultiplier` or your lamp goes black.** `ULightComponent::SetLightBrightness` — the function that divides by `TextureMultiplier` — is inside `#if WITH_EDITOR` (`Source/Runtime/Engine/Private/Components/LightComponent.cpp:582`). At runtime only `ComputeLightBrightness` (`:560-579`) applies, doing an unguarded `LightBrightness *= IESTexture->TextureMultiplier`. A hand-built profile left at 0 does not make the lamp "wrong", it makes it silently black. Also: only 32 distinct profiles by default (`r.IESAtlas.MaxProfileCount`).

**Contact shadows are a free win here.** `ContactShadowLength` is a screen-space trace needing no BVH and no distance field — a cheap way to reintroduce the small-scale contact darkening that one-bounce Lumen will miss.

### Notes

**Verify parameter names at startup; do not hardcode.** The `/Engine` material parameter names above were read out of `.uasset` name tables, which prove that a parameter *expression* exists but not which `FName` binds to which pin. `EmissiveMeshMaterial`'s two names are the exception — they are independently corroborated by `Source/Runtime/Renderer/Private/SceneVisibility.cpp:5836`, which constructs `FColoredTexturedMaterialRenderProxy(..., Color, NAME_Color, SurfaceTexture, NAME_LinearColor)` against the signature at `MaterialRenderProxy.h:345`. Everything else — `BasicShapeMaterial`'s `Color`/`Roughness`, `VertexPaint_*`'s `Diffuse`/`Normal` family, `M_Grid`'s spaced names like `"Grid 1 Texture"` — should be enumerated with `GetAllTextureParameterInfo` / `GetAllScalarParameterInfo` at startup, asserted, and logged-and-fallen-back-to-`VertexColorMaterial` if missing. Setting a name the parent does not expose is a completely silent no-op.

`GetAllStaticSwitchParameterInfo` (`MaterialInterface.h:962`) and `GetAllStaticComponentMaskParameterInfo` (`:963`) are inside `#if WITH_EDITORONLY_DATA` (guard opens `:961`). Touching them in that startup routine compiles in the editor and **fails to compile** in a packaged Game target.

**`GEngine->VertexColorMaterial` is null in every packaged build.** `UEngine::InitializeObjectReferences` loads it at `Private/UnrealEngine.cpp:3558`, inside `if (AllowDebugViewmodes())` opened at `:3549`. `AllowDebugViewmodes()` (`Source/Runtime/RenderCore/Private/ShaderCore.cpp:579`) returns false whenever `FPlatformProperties::RequiresCookedData()` — which is every cooked build, Development included. It also returns false in a commandlet without `-AllowCommandletRendering`, and unconditionally false if `r.ForceDebugViewModes==2`. Always `LoadObject<UMaterial>(nullptr, TEXT("/Engine/EngineDebugMaterials/VertexColorMaterial"))`. `DebugMeshMaterial` (`:3574`) and `EmissiveMeshMaterial` (`:3575`) are loaded *outside* the gate and are safe off `GEngine`.

That same commandlet branch weakens any inference that `[Engine.StartupPackages]` membership guarantees cooking. Treat the explicit `+DirectoriesToAlwaysCook` entry as **required**, and verify by inspecting the cooked output rather than reasoning about it.

**`VertexPaint_2Tex_Color` also references `/Engine/Engine_MI_Shaders/T_Normal` and `T_Emissive`** (and only those two — a third reference commonly cited does not exist). All the `VertexPaint_*` materials additionally pull material functions from `/Engine/Functions/Engine_MaterialFunctions01/Shading/` (`ConvertFromDiffSpec`, `PowerToRoughness`). The cooker should follow those transitively out of a package it is already cooking, but that is precisely the inference chain not to trust — check for the `Engine_MaterialFunctions01` packages in the cooked output.

**`CreateTransient` texture hygiene.** `SRGB` defaults to `true` (set in `UTexture`'s constructor) and becomes `TexCreate_SRGB` on the RHI texture. Leave it on for albedo; you **must** set it false for normal maps, height, roughness and masks. `PF_B8G8R8A8` is BGRA byte order — getting it backwards produces a plausible-but-wrong palette that is easy to rationalise away. Exactly one mip is created and there is no runtime mip generation; undersampled rock walls will shimmer badly against volumetric fog. Textures are outered to `GetTransientPackage()` with `RF_Transient` and will be collected without a `UPROPERTY` or `TStrongObjectPtr`.

Two allocation defects worth knowing before reaching for block-compressed formats: `UTexture2D::CreateTransient` (`Private/Texture2D.cpp:1291-1300`) computes `NumBlocksX`/`NumBlocksY` by integer division *before* the `<= 0` guard and never checks that dimensions are block-multiples; `UVolumeTexture::CreateTransient` (`Private/VolumeTexture.cpp:59-94`) validates X and Y against block size but **never Z**, while the `Realloc` at `:86` divides by `BlockSizeZ`. Both are harmless at the `PF_B8G8R8A8` default and are memory-corruption traps otherwise. The volume-texture mip is also `Realloc`'d but never zero-filled.

**PMC vertex-colour sRGB defaults disagree between create and update.** `CreateMeshSection_LinearColor` declares `bSRGBConversion = false` (`ProceduralMeshComponent.h:193`); `UpdateMeshSection_LinearColor` declares `= true` (`:230`). Both feed `FLinearColor::ToFColor(bSRGBConversion)` (`.cpp:541` and `:648`). For a game that rebuilds sections every time a wall is drilled, **the world silently changes colour the first time a section is updated**. Pass the flag explicitly at both call sites. Separately, if `VertexColors.Num() != NumVerts` the component substitutes `FColor(255,255,255)` (`.cpp:576`) — an off-by-one in the mesher shows up as white bricks, not as an error.

### Notes

**The module map is better than the plugin names suggest.** `GeometryCollectionEngine`, `FieldSystemEngine` and `ChaosSolverEngine` all live under `Engine/Source/Runtime/Experimental/` and are plain runtime engine modules — you add them to `.Build.cs` with **no `.uproject` change**. The similarly-named plugins contain only Editor/Sequencer/Nodes modules. One caveat: `GeometryCollectionEngine.Build.cs` adds `"UnrealEd"` and `"EditorFramework"` to `PublicDependencyModuleNames` under `if (Target.bBuildEditor)`, so any DeepCore module that *publicly* depends on it inherits a public `UnrealEd` dependency in editor targets.

`FractureEngine` genuinely is a Runtime module (`Fracture.uplugin` declares `"Type": "Runtime"`, and `FractureEngine.Build.cs` pulls only Runtime modules — including `MeshUtilitiesCommon`, which is `Source/Runtime/MeshUtilitiesCommon`, not Developer). Enabling `Fracture` transitively enables `PlanarCut` (its own Beta plugin) and `GeometryProcessing` (also Beta). Both `FractureEngine` and `PlanarCut` have `LoadingPhase: PostEngineInit` — do not call into them from an earlier-initialising module.

**The `UClusterUnionComponent` example you will find online is wrong for 5.8.** The common pattern — `AddComponentToCluster(Comp, {}, /*bRebuildGeometry*/ false)` in a loop, then `ForceRebuildGTParticleGeometry()` — is broken twice over. `ForceRebuildGTParticleGeometry` is `UE_DEPRECATED(5.4, "Cluster unions now incrementally update their geometry. A force rebuild should never be needed - this function will no longer book-keep properly either.")` (`ClusterUnionComponent.h:348`), and `bRebuildGeometry` gates the one call that now does the work: `ClusterUnionComponent.cpp:258` is `if (bRebuildGeometry) { AddGTParticleGeometry(Objects); }`. Passing false skips it and then hands recovery to a function Epic says no longer book-keeps. **Use the default `bRebuildGeometry = true` and delete the force-rebuild call.**

Also: `bEnableDamageFromCollision` defaults to **true** (`ClusterUnionComponent.cpp:117`). Turn it off for load-bearing structure you do not want spontaneously shedding. And `SetMassOverrideInKg` is recomputed from remaining members whenever the cluster breaks — re-apply it from `OnComponentRemovedEvent`.

**The geometry-collection custom renderer has two traps that make it invisible with no error.** `UGeometryCollectionComponent::CustomRendererType` and `bOverrideCustomRenderer` are `protected` with no public setter (`GeometryCollectionComponent.h:1560`, `:1564`). The working route is `UGeometryCollection::CustomRendererType`, which *is* public (`GeometryCollectionObject.h:637`) — `InitializeCustomRenderer` (`GeometryCollectionComponent.cpp:3696`) reads `bOverrideCustomRenderer ? CustomRendererType : (RestCollection ? RestCollection->CustomRendererType : nullptr)`, so setting it on your runtime-built asset works with the override flag left at its false default. Second: `SetRestCollection` only calls `InitializeCustomRenderer()` inside `if (IsRegistered())` (`:5175`). **Call `RegisterComponent()` before `SetRestCollection`**, or — because `CreateSceneProxy` also returns nullptr — you get a component that simulates and draws nothing.

**PMC collision is the largest quantifiable perf trap in a dig-driven game.** `GetPhysicsTriMeshData` (`ProceduralMeshComponent.cpp:943`) concatenates **every** collision-enabled section into one `FTriMeshCollisionData`, so removing one brick re-cooks the entire component: full vertex copy, index flatten, `CleanTrimesh` spatial-hash weld, per-triangle validation, particle array build, full `FTriangleMeshImplicitObject` BVH. `bUseAsyncCooking` does not save you — `UpdateCollision` (`:1034`) allocates a *brand new* `UBodySetup` and calls `AbortPhysicsMeshAsyncCreation` on every queued one, so rapid drilling produces a stream of aborted cooks and UObject garbage. The synchronous path calls `RecreatePhysicsState()`, which drops all contacts.

Mitigations, in order of value: don't use tri-mesh collision for brick terrain at all (use the `FKBoxElem` path above); failing that, split terrain into many small PMC chunks; set `bEnableCollision=false` on decorative sections; and set `p.EnableMeshClean=0` if your generator already emits clean welded geometry. Note `FKBoxElem(float,float,float)` takes **full extents**, not half-extents — a classic 2× error.

Finally, `UBodySetup::IsRuntime()` (`BodySetup.cpp:403`) requires the outer to resolve to a game world; an orphaned body setup silently gets no collision.

**Do not build on `FClusterUnionStressSolver`.** It exists (`Private/Chaos/ClusterUnionStressSolver.cpp`) with real cvars and looks exactly like the structural-load-collapse feature a mining game wants. A tree-wide grep finds the symbol in exactly two files — its own `.cpp` and `.h` — and zero references anywhere else in `Engine/Source` or `Engine/Plugins`. It is not wired into the solver. Drive breaking yourself via strain or explicit removal.

### Notes

**`AIModule` publicly depends on `NavigationSystem`, `GameplayTags` and `GameplayTasks`**, so those arrive transitively. You never have to spawn an `ARecastNavMesh`; you are paying a build-size cost, not a runtime one.

**`FGraphAStar` usage rules.** The searcher holds the graph **by reference** (`const TGraph& Graph;` at `GraphAStar.h:320`, ctor `:345`) — the tile map must outlive it and must not be reallocated out from under a long-lived instance. `FNodeMap` is a `TMap<FGraphNodeRef, int32>`, so `FNodeRef` needs `GetTypeHash` (fine for `int32`/`FIntVector`, a compile error for a bare custom struct). `Policy::bReuseNodePoolInSubsequentSearches` defaults false and `FatalPathLength` to 10000 — for hundreds of units, define a custom policy with pool reuse and keep one instance per worker thread. `DoRangeCheck` defaults false, swapping in `FRangeChecklessAllocator`: a bad `FNodeRef` reads out of bounds *silently*. Develop with it true.

Put `GetNeighbourCount` on the **graph**, not the filter — `:328`/`:390` dispatch `GetNeighbourCountV2(Graph, ...)`, and the header's comment placement is misleading. Without it, iteration stops at the first invalid neighbour ref.

**Recast's real defaults are worse than the struct defaults.** `Config/BaseEngine.ini:3053` sets `CellSize=19.f` and `:3055-3057` sets `NavMeshResolutionParams[0..2]` to 38/19/19; the `25.f` you will find in `FNavMeshResolutionParam::CellSize` (`RecastNavMesh.h:559`) is overridden. At `TileSizeUU=1000` (`:3052`) that is ~53×53 voxel columns per tile, ~1.7× more than the commonly-quoted figure. Note also that `ARecastNavMesh::CellSize` (`:712`) is `UE_DEPRECATED(all, "Use NavMeshResolutionParams ...")` — setting it does nothing.

Dirty-area growth uses `GrowBoundingBox(TileBB, /*bIncludeAgentHeight*/ false)` when `ai.nav.UseTightBoundExpansion` is on (the default), i.e. one `AgentRadius` (`RecastNavMeshGenerator.cpp:1804-1811`, `:6596-6601`). The `AgentRadius*2 + cs` formula widely quoted is the branch commented `// Deprecated`.

If you do use Recast: set `RegionPartitioning` to `Monotone` (the `Watershed` default is tuned for offline bake quality, not per-frame regeneration), and use navigation invokers to bound tile count — but see the trap about invokers silently discarding all dirty areas.

**Mass buys you data layout, not behaviour authoring.** `UStateTree` cannot be authored at runtime under any configuration: its compiled payload (`Frames`, `States`, `Transitions`, `Nodes`, `DefaultInstanceData` — `StateTree.h:455-471`) is `private` in a block opening at `:432`, the only writer is `friend struct FStateTreeCompiler` wrapped in `#if WITH_EDITOR` (`:683-684`), and `FStateTreeCompiler` exists only in `StateTreeEditorModule`, which the `.uplugin` marks `"Type": "UncookedOnly"`. That kills the StateTree half of `MassAIBehavior` (its `MassLookAt*` gaze feature is not StateTree-based, but still requires the Experimental MassAI plugin). **You will write behaviour as hand-rolled C++ processors regardless of whether you adopt Mass.** That fact should drive the adopt/don't-adopt decision.

`MassGameplay.uplugin` is `"IsExperimentalVersion": true`, `"EnabledByDefault": false`, and force-enables ZoneGraph, PoseSearch, ZoneGraphAnnotations, SmartObjects, StateTree and DataValidation — a large experimental surface for a project that currently enables exactly one plugin. Plain `FMassEntityManager` + `FEntityBuilder` + your own phase manager needs **none** of it.

**`UBehaviorTree` runtime construction, honestly.** It works: `RootNode` is a plain `UPROPERTY` (only `BTGraph` is `WITH_EDITORONLY_DATA`, `:23-27`), `UBTCompositeNode::Children` is a public `TArray<FBTCompositeChild>` (`:93`), and `UBehaviorTreeManager::LoadTree` does the full runtime setup — `StaticDuplicateObject` of the root, `InitializeNodeHelper` for execution indices, memory-offset packing — with no editor guard anywhere. But every node must be a `UObject` you keep referenced, `LoadedTemplates` caches per-asset-pointer so rebuilding in place hands you a stale template, and for a job-based mining sim this is more hand-written wiring than a plain state machine. The blackboard side works too (`UBlackboardData::Keys` at `:61` is outside the `WITH_EDITORONLY_DATA` block closing at `:57`), but `UpdatePersistentKey` calls `PropagateKeyChangesToDerivedBlackboardAssets`, implemented at `BlackboardData.cpp:219-230` as a full `TObjectIterator<UBlackboardData>` UObject-space scan — **per key added**, with no editor guard. A POD struct on your controller is faster and type-safe.

**Detour crowd is structurally coupled to Recast.** `UCrowdManager::SetAgentMovePath` takes an `FNavMeshPath*` and the system is built on `dtNavMesh` internals — if you path on your own grid there is no supported way to feed it. In narrow tunnels, RVO-style avoidance also tends to push agents into walls the navmesh believes are walkable. A simple queueing/shuffling rule on the tile grid looks better and costs far less.

**Shader authoring needs a second module.** `ELoadingPhase::PostConfigInit` modules load in `FEngineLoop::AppInit` at `LaunchEngineLoop.cpp:6809`; `CompileGlobalShaderMap` runs at `:3307`; `ELoadingPhase::Default` only at `:4682`. `DeepCore.uproject` declares `"Default"`, so a mapping registered from `FDeepCoreModule::StartupModule` arrives after the global shader map was already built — the shader *type* was never statically registered in time. **Console variables survive Shipping; the console UI may not.** Everything in `IConsoleManager.h` is wrapped in `#if !NO_CVARS` with empty no-op stand-ins otherwise, and `NO_CVARS` is not defined in `Build.h` — so registrations work in a normal Shipping build. **Off-thread UObject rules, stated plainly.** On a generation worker: do not `NewObject`, do not `SpawnActor`, do not modify a `UPROPERTY` container, do not create or destroy components. Generate plain structs (vertex/index/normal arrays) and hop back with `AsyncTask(ENamedThreads::GameThread, ...)` to touch anything UObject. If a worker must merely *read* a UObject that could be collected, hold it with a `TStrongObjectPtr` created on the game thread — do **not** reach for `FGCScopeGuard` (`Source/Runtime/CoreUObject/Public/UObject/GarbageCollection.h`), which held across a long job stalls GC engine-wide and shows up as a hitch attributed to something else entirely.

## SILENT NO-OPS AND TRAPS

**Read this section before writing code in any domain.** Every entry compiles cleanly and produces no error at runtime. Grouped by domain; the first four have already cost this project time or would have.

### Rendering / Lumen visibility

1. **HISM contributes zero GI, unconditionally.** `HierarchicalInstancedStaticMesh.cpp:807` sets `bVisibleInLumenScene = false` in the constructor body, overwriting what the base constructor computed at `StaticMeshSceneProxy.cpp:481`. No cvar recovers it without Nanite. **Use plain ISM.**

2. **PMC's BLAS is created once, at proxy construction, only if `IsRayTracingEnabled()` was true then** (`ProceduralMeshComponent.cpp:157-180`). Terrain spawned before RT is on is permanently absent from the TLAS — and since HWRT is the only Lumen branch here, permanently unlit. Toggling `r.RayTracing.Enable` later does not retroactively create BLASes; you must force a render-state recreate on every PMC. This is why the boot gate in **Start here #2** is not optional.

3. **`r.RayTracing.Geometry.ProceduralMeshes=0` makes the entire world vanish from Lumen and RT shadows** while every Lumen cvar still reads back enabled. `HasRayTracingRepresentation()` returns true unconditionally (`ProceduralMeshComponent.cpp:424`) so `bVisibleInLumenScene` is set, but `GetDynamicRayTracingInstances` early-returns (`:428`). A scalability or device profile can set this.

4. **A runtime-built `UStaticMesh` can drop out of Lumen with no diagnostic at all.** `StaticMeshSceneProxy.cpp:385` reads `if (bSupportRayTracing && !ensureMsgf(RenderData->RayTracingProxy, ...))`, and `bSupportRayTracing` is itself `IsRayTracingAllowed() && StaticMesh->bSupportRayTracing` (`:379`). Build the mesh while `IsRayTracingAllowed()` is false and the ensure never fires — silent absence, not even an ensure.

5. **`ShadowCacheInvalidationBehavior::Static` on a PMC produces permanently stale shadows.** Covered in Start here #3. Use `Rigid`.

6. **`ShadowCacheInvalidationBehavior` set after `RegisterComponent()` does nothing** — the proxy snapshots it at construction (`PrimitiveSceneProxyDesc.cpp:177`).

7. **`ULightComponent::ShadowBias`/`ShadowSlopeBias`/`ShadowSharpen`/`ShadowResolutionScale` are inert under VSM.** Tuning them to chase brick-scale acne is wasted effort; the knobs are `r.Shadow.Virtual.NormalBias`, `.ScreenRayLength`, and the `SMRT.*Local` family.

8. **`r.Shadow.Virtual.ShowStats` is deprecated (5.7).** Use `r.Shadow.Virtual.Stats.Visible`. Old ini snippets silently do nothing.

9. **Lumen hit lighting silently downgrades to surface cache** — which means black on this project's geometry — if RayGen shaders are unavailable, or if a scalability profile sets `r.Lumen.HardwareRayTracing.HitLighting.Allowed=0`. `LightingMode` still reads 1.

10. **Every `r.LumenScene.SurfaceCache.*` / `r.LumenScene.Radiosity.*` cvar and the `LumenSkylightLeaking` / `LumenSurfaceCacheResolution` post-process settings are inert here** (no mesh cards, ever — `LumenMeshCards.cpp:887-956`). You still pay Lumen scene bookkeeping for zero benefit.

11. **`r.VolumetricFog.InjectRaytracedLights` defaults to 0.** Switch a lamp to ray-traced shadows with MegaLights off and it silently loses its god-ray — the RayGen injection path exists and is fully implemented, just disabled.

12. **`r.LocalFogVolume.MaxDensityIntoVolumetricFog` clamps to 0.01** and **`r.LocalFogVolume.GlobalStartDistance` culls within 10 metres**. A dust cloud that "does nothing" is almost certainly one of these two.

13. **A local fog volume outside the volumetric fog grid is shaded only by a directional light + skylight** — i.e. by nothing, underground. It is *only* useful via `RenderIntoVolumetricFog=1`.

14. **`SetIESTexture` with `TextureMultiplier == 0` makes the lamp black, not merely wrong.** `ComputeLightBrightness` (`LightComponent.cpp:560-579`) multiplies unguarded; the editor-only `SetLightBrightness` that would have divided is compiled out (`:582`).

49. **A "Wave Player" node fed a `USoundWaveProcedural` outputs silence.** It routes to `FSoundWaveProxyReader::InitializeDecoder` (`SoundWaveProxyReader.cpp:393`), which needs `GetRuntimeFormat()` + a registered decoder over `GetResourceData()`; `bProcedural` sound waves have no cooked/compressed data by design (`SoundWave.cpp:2333`, `:2682`). Wave Player only works on cooked `USoundWave` assets. Play imported WAVs via `QueueAudio` or a custom `ISoundGenerator` instead.

50. **Nothing keeps your MetaSound builder alive** — the registry stores `TWeakObjectPtr` (`MetasoundDocumentBuilderRegistry.h:23`), and the transient `UMetaSoundSource` is owned *through* the builder. Losing the builder silences a playing voice.

51. **A transient `USoundSubmix` held only by a raw pointer is collected and routing quietly reverts to master.** Unregistered submixes also swallow sends.

52. **`SetSubmixEffectChainOverride` replaces the whole chain** despite sitting next to `AddSubmixEffect`.

53. **`QueueAudio` silently rejects a zero-length or misaligned buffer** (`SoundWaveProcedural.cpp:35`) via `ensure` — once per session in Shipping, so a systematically misaligned producer degrades to intermittent silence.

54. **`ULineBatchComponent`'s default `BatchID` is `INVALID_ID`, not 0** (`LineBatchComponent.h:149-193`), while `FBatchedLine`'s own member default is 0 (`:47`). Clearing by ID 0 clears nothing.

### Engine services

65. **A `UTickableWorldSubsystem` that omits `Super::Initialize` never ticks and asserts nothing.** `bInitialized` stays false, `GetTickableTickType()` keeps returning `Never` (`WorldSubsystem.cpp:67-76`), and the `checkf(IsInitialized())` in `Tick` (`:86-89`) can never fire because `Tick` is never called. ## DEAD ENDS

Do not reach for these. One line of reasoning each.

### Geometry
- **Nanite at runtime** — `NaniteBuilder` is a `Source/Developer` module referenced only under `Target.bBuildEditor` (`Engine.Build.cs:422/449`); `IBuilderModule::Get()` uses `LoadModuleChecked` and hard-fails elsewhere. `SetNaniteSettings` is inside `WITH_EDITORONLY_DATA`.
- **Mesh distance fields at runtime** — only produced by `FStaticMeshRenderData::Cache → CacheDerivedData`, inside the editor-only build path (`StaticMeshBuild.cpp:122+`); `r.GenerateMeshDistanceFields` is `ECVF_ReadOnly` (`DistanceFieldAtlas.cpp:59`).
- **Switching PMC → `UDynamicMeshComponent` to fix software Lumen** — 5.8 *removed* DF support from dynamic meshes: `bWillHaveDistanceField = false` hardcoded (`BaseDynamicMeshSceneProxy.cpp:66`), `SetNewDistanceField` does `ensureMsgf(false, ...)` (`:869`), and `EDynamicMeshComponentDistanceFieldMode` is `UE_DEPRECATED(5.0)` (`BaseDynamicMeshComponent.h:94`). Migrate for other reasons; HWRT stays mandatory.
- **The full `UStaticMesh::Build()` path for runtime distance fields** — editor-only, and `DeepCoreMaterials.cpp` proves the project is *not* editor-linked (`#if WITH_EDITOR` guard `:9`–`:334` with a deliberate cooked-build fallback). Taking it would permanently forfeit a shippable standalone build.
- **`UCustomMeshComponent`** — its proxy sets only `bDynamicRelevance` and inherits `HasRayTracingRepresentation() == false`, so it is invisible to Lumen in both SWRT and HWRT. Strictly worse than PMC.
- **`FDynamicMeshBuilder`** — its own header says "meant to be easy to use, not fast"; one-frame batches, no persistent primitive, no RT geometry, no collision. Debug drawing only.
- **`RealtimeMeshComponent`** — not in the tree; third-party, and it could not produce a `FDistanceFieldVolumeData` either.
- **Landscape / heightfield as a Lumen SWRT escape hatch** — `SupportsHeightfieldRepresentation()` is true on exactly one proxy in the engine (`LandscapeRender.cpp:1717`), it needs heightmap assets and an editor-only import path, and a 2.5D heightfield cannot represent a cave.
- **`UHierarchicalInstancedStaticMeshComponent`** — see trap #1. Correctness dead end, not a perf trade.

### Lighting
- **Lumen software ray tracing** and every `r.Lumen.TraceMeshSDFs` / `MeshSDF.*` cvar — the software branch of `UpdateVisibleInLumenScene` cannot be satisfied by any runtime geometry.
- **Lumen surface cache / radiosity** — no mesh cards, ever.
- **Screen-space light shafts** (`bEnableLightShaftBloom`/`Occlusion`) — hard-gated to directional lights (`LightShaftRendering.cpp:122-130`). There is no sun. God-rays must come from the fog froxel grid.
- **SkyLight distance-field AO** — the whole `OcclusionMaxDistance`/`Contrast`/`MinOcclusion`/`OcclusionTint`/`OcclusionExponent`/`OcclusionCombineMode` block needs a mesh DF at render time. Settable from C++, does nothing.
- **Custom light functions / gobos** — need a `MD_LightFunction` material; new materials cannot be compiled at runtime, and the only shipped one is flat white. Animate `SetIntensity`/`SetLightColor` instead.
- **Particle/mesh-voxelized volumetric fog** — needs a Volume-domain material asset. `ULocalFogVolumeComponent` covers the same art need.
- **MegaLights software fallback** — Global SDF based; dead here. MegaLights is HWRT-or-nothing.
- **Lightmass, `ULightmassPortalComponent`, precomputed shadow depth maps** — `r.AllowStaticLighting=False` and there is nothing to bake.
- **`AAudioVolume`-style reverb via brushes** — see Audio below.

### Materials
- **Authoring a `UMaterial` at runtime** — the root constraint. `FMaterial::CacheShaders` only compiles inside `#if WITH_EDITORONLY_DATA`; `UMaterialExpression` is `CLASS_Optional` and harvested out of cooked packages. Fails silently to the default material.
- **`FCustomPrimitiveData` / per-instance custom data as a per-brick channel** — no `/Engine` material reads either. Vertex colours are strictly better on both correctness and cost.
- **`UMaterialParameterCollection`** — materials bind a collection by `StateId` GUID at shader-compile time; you cannot compile a consumer, and the one shipped MPC is an art-tool asset nothing references.
- **`URuntimeVirtualTexture`** — read and write are both material-graph-only nodes; zero shipped materials contain either. Also fundamentally a large-flat-surface caching technique, wrong for a destructible cave.
- **Changing blend mode / two-sidedness / shading model / static switches at runtime** — `FMaterialInstanceBasePropertyOverrides` and `SetBasePropertyOverrides` are `#if WITH_EDITORONLY_DATA` (`MaterialInstance.h:594-614`); `SetStaticSwitchParameterValueEditorOnly` is named for what it is. Keep separate engine parents per variant.
- **`UMaterialInstanceConstant` at runtime** — every setter on it is `*EditorOnly`. Use `UMaterialInstanceDynamic`.
- **Tinted or textured deferred decals** — `/Engine` ships two decal materials and neither exposes a single parameter. Fake wall marks with an offset PMC quad.
- **`LineSetComponentMaterial` / `PointSetComponentMaterial` on ordinary geometry** — WPO billboarding materials that expect line direction in the tangent channel and thickness in UV0; applied to a brick mesh they deform it.
- **Runtime mip generation for `CreateTransient` textures** — `MipGenSettings` is a cook-time concept; exactly one mip is allocated. Build the chain yourself, or use a render target with `bAutoGenerateMips`.
- **Enabling Substrate to get around material limits** — `r.Substrate` is `ECVF_ReadOnly`, default 0, not set by this project, and it is orthogonal: it changes how graphs describe shading, not whether you can compile one.

### Physics / destruction
- **`FGeometryCollectionRenderData::Create`** — both `#if WITH_EDITOR` and in a `Private` header. The single blocker on native geometry-collection rendering.
- **`UGeometryCollection::CreateSimulationData` / `EnsureDataIsCooked`** — `#if WITH_EDITOR`, DDC-backed. Use the free `BuildSimulationData` instead; that is the whole trick.
- **`FGeometryCollectionEngineConversion::AppendStaticMesh`** — bodies wrapped in `#if WITH_EDITORONLY_DATA` (`:168/522/621`); they compile at runtime and do nothing. Feed `FGeometryCollection` your own arrays.
- **Geometry-collection Nanite path** — `NaniteBuilder` under `bBuildEditor`; `HasNaniteData()` always false at runtime. Moot given the RenderData blocker anyway.
- **`Chaos::Cooking::BuildSingleTrimesh`** — `ENGINE_API`, but in `Runtime/Engine/Internal/`, and UBT only adds Internal include paths for matching-scope or engine modules (`UEBuildModule.cs:737`). Not on your include path.
- **Chaos Cloth / ChaosClothAsset / ChaosOutfitAsset / ChaosFlesh** — all asset-first with no runtime-construction path and nothing free to borrow.
- **Chaos Caching** — the premise is recording into a saved asset; you cannot persist one at runtime.
- **ChaosNiagara** — downstream of Niagara. Drive debris from `OnChaosBreakEvent` delegates instead.
- **`UFieldSystemAsset` / `AFieldSystemActor`** — unnecessary; the whole useful field surface is direct C++ on the component with `NewObject`'d nodes.
- **`Plugins/Experimental/Iris`** — Beta (`IsBetaVersion: true`, `VersionName 0.1`), disabled by default, and irrelevant to a single-player game.

### AI / navigation
- **`UStateTree` / `UStateTreeComponent`** — hard block. Compiled payload is `private` (`StateTree.h:432+`), the only writer is `friend struct FStateTreeCompiler` inside `#if WITH_EDITOR` (`:683-684`), and that compiler lives only in an `UncookedOnly` module. No runtime authoring path exists under any configuration.
- **`MassAIBehavior`'s StateTree layer** — inherits the block in full. Adopting Mass gets you the data architecture, not Epic's behaviour authoring.
- **ZoneGraph / `MassZoneGraphNavigation` / MassCrowd** — spline/lane graphs baked from editor-placed actors. No runtime lane-authoring story fits a world the player rewrites with a drill.
- **EQS** — `UEnvQuery::Options` is `protected` with `friend class UEnvQueryManager` (`EnvQuery.h:29-36`); there is no public mutator at all, so `NewObject` gets you nothing. "Nearest unclaimed ore tile" is a direct query against your own grid.
- **SmartObjects** — the only public slot adder is literally named `DebugAddSlot()`, and slot behaviours route to GameplayBehavior or StateTree. A mining game's "smart objects" are already entries in your tile grid.
- **`UCrowdManager` / Detour crowd** — structurally coupled to `dtNavMesh`; `SetAgentMovePath` takes an `FNavMeshPath*`.
- **HTNPlanner, MLAdapter** — research-grade, no asset-free runtime authoring path, and job assignment is a scheduling problem, not a planning one.
- **`UMassEntityConfigAsset`** — optional, not mandatory. Listed only to be explicit that it is off the table while Mass itself is not.

### World structure
- **World Partition** — creation and streaming generation are entirely `#if WITH_EDITOR` (`WorldPartition.h:166-168`), and cells are generated from actor descriptors that only exist for actors saved in a level package. Spawned actors have none.
- **Level Instances** — `ALevelInstance` is keyed on `TSoftObjectPtr<UWorld>` (`LevelInstanceActor.h:29`). Every level instance *is* a level asset.
- **HLOD** — proxies are built at cook from placed static meshes and are themselves cooked assets. There is no runtime path and PMC has no static mesh to merge.
- **`ULevelStreamingDynamic::LoadLevelInstance`** — still loads a named `UWorld` package.

### VFX / audio
- **Niagara, in every form** — system/emitter authoring and all script compilation are `#if WITH_EDITORONLY_DATA`, and no general-purpose `UNiagaraSystem` ships in `/Engine`. `EnabledByDefault` is a red herring: it is linkable with nothing to drive.
- **Cascade** — same asset problem plus legacy, plus its renderers enforce `MATUSAGE_ParticleSprites` / `MeshParticles` / `BeamTrails` at runtime and no free material carries them.
- **Niagara Data Channels** — downstream of a dead end.
- **`UMaterialBillboardComponent` as a sprite emitter** — `FMaterialSpriteElement` has no per-element position or colour; every element renders at the component origin.
- **`AAudioVolume`** — derives from `AVolume` and depends on editor-authored brush geometry. Use `ActivateReverbEffect` (tag-based, no volume actor) or a submix + reverb preset. **But see GAP 4 below — `Plugins/AudioGameplayVolume` may reopen this door.**
- **`USoundWave::GetImportedSoundWaveData`** — both overloads `#if WITH_EDITOR` (`SoundWave.h:1345/1348`). Use `FWaveModInfo::ReadWaveInfo`. Avoid `USoundWave::OverrideWaveData` — `UE_EXPERIMENTAL(5.8, "May be altered or removed")`.
- **Post-process materials and the `BL_*` blend locations** — need an `MD_PostProcess` material asset. `SubscribeToPostProcessingPass` with your own global shader reaches the same insertion points.
- **Asset-typed post-process inputs** — `FWeightedBlendables`, `BloomConvolutionTexture`, `BloomDirtMask`, `VignetteTexture`, `LensFlareBokehShape`, `ColorGradingLUT`. Standard bloom, non-textured vignette and the numeric grading wheels cover the look.
- **`LightFunctionAtlas`** — would be ideal for flickering gobos in beams, but needs a `MD_LightFunction` material; the only free one is flat white. Also `r.LightFunctionQuality <= 0` disables the show flag globally.

### Rendering extension
- **Registering a new `EMeshPass` from a game module** — fixed enum with a `static_assert` on mask width (`MeshPassProcessor.h:613`).
- **`AddSimpleMeshPass` for rendering your geometry to your own target** — both required parameter types are Renderer-private; without an `FScene` you cannot use primitive-ID streams, which `FLocalVertexFactory` requires.
- **`Lumen::UseHardwareRayTracing()` and other Renderer-private Lumen predicates** — not exported. Query the cvars through `IConsoleManager` instead.

## Unverified — check before relying on

Everything here is plausible and was reasoned from adjacent source, but was **not** confirmed. Do not build on any of it without opening the file first.

1. **Exact MetaSound node *pin* names.** Node class names are verified; input/output vertex names are built per-node elsewhere and were not enumerated. Dump them at runtime with `FindNodeInputs`/`FindNodeOutputs` before writing graph code.
2. **`BasicShapeMaterial`'s parameter names `Color` and `Roughness`.** The vector and scalar parameter *expressions* are confirmed present, but `Roughness`/`BaseColor` also appear as `FExpressionInput` property names on every material's name table, so their presence is not proof. Verify with `GetAllVectorParameterInfo`/`GetAllScalarParameterInfo`.
3. **`VertexColorMaterial` being `TwoSided`.** Inferred from the name table (present there, absent from `BasicShapeMaterial`'s and `VertexPaint_2Tex_Color`'s), which is self-consistent but is the same inference the catalog otherwise refuses to trust. Confirm at runtime with `UMaterialInterface::IsTwoSided()`.
4. **`r.Shadow.Virtual.UseReceiverMaskLocal`'s default.** The cvar exists (`VirtualShadowMapArray.cpp:775-776`, read at `:849`); the claimed `false` default was not confirmed.

15. **`r.ForceDebugViewModes=2`'s effect on the base-pass shaders of `VertexColorMaterial` itself** (as opposed to only the debug-viewmode permutations). Re-test the packaged look if that cvar is ever set.
16. **Whether a `UMaterialInstanceDynamic` over `EmissiveMeshMaterial` can legally be assigned to `UPointSetComponent`/`ULineSetComponent`.** Those use custom vertex factories whose proxies were not checked for a usage test — and their stock materials are `BLEND_Opaque` anyway.

Whether that is acceptable for a chunk that changes on every dig is the main reason to keep `UDynamicMeshComponent` for the active face.
19. **Actual wall-clock cost of a Recast tile rebuild on this machine.** The structural model is solid; the milliseconds are not measured. Only relevant if Recast is ever reconsidered.

21. **Whether enabling the RenderDoc capture plugin is acceptable under the project's rules.** It is an engine plugin with no content, so probably fine as a development-only `.uproject` entry — but that is a project-policy call.

### P0 — architectural decisions being made blind

**5. Camera control — zero coverage.** RTS camera was in the brief and appears in no survey. Two competing engine answers with very different maturity: `Plugins/Cameras/EngineCameras` (the `UCameraShakeBase`/`UMatineeCameraShake` line) versus `Plugins/Cameras/GameplayCameras` — note the latter is `"EnabledByDefault": true` **and** `"IsExperimentalVersion": true`, an unusual combination meaning it is already in your build. Also unexamined: `APlayerCameraManager` camera modifiers (`UCameraModifier`, plain `UObject`, `NewObject`-able) in `Source/Runtime/Engine/Classes/Camera/`, and `Source/Runtime/CinematicCamera`. Shakes and modifiers are asset-free; `GameplayCameras` rigs are asset-driven.

**6. Movement — no answer for units, none at all for vehicles.** §E says "drive movement directly" without saying what with; §D suggests "a simulating body plus your own suspension raycasts" — a substantial system with no engine reference. Start with the lightweight options nobody named: `Source/Runtime/Engine/Classes/GameFramework/FloatingPawnMovement.h` and `NavMovementComponent.h` (asset-free, trivial). Then `Plugins/Experimental/Mover` (`IsExperimentalVersion: true`) — Epic's designated `UCharacterMovementComponent` replacement, with `Plugins/Experimental/ChaosMover` and `Plugins/Experimental/MoverExamples` alongside. For vehicles, `Plugins/Experimental/ChaosModularVehicle` is a better fit than `ChaosVehiclesPlugin` for a brick-built machine, since it composes from modules rather than requiring a skeletal-mesh wheel rig.

**7. Water and lava hazards — not mentioned once.** Likely a real dead end, but the verdict should be *recorded*. `Plugins/Experimental/Water` (`EnabledByDefault: false`, `IsExperimentalVersion: true`), `Plugins/Experimental/WaterAdvanced`, `Plugins/Experimental/Buoyancy`. Expect a negative result — water bodies are spline/landscape-driven actors. The asset-free substitute is probably `APhysicsVolume` (`Source/Runtime/Engine/Classes/GameFramework/PhysicsVolume.h`, which has `bWaterVolume`, `TerminalVelocity`, `FluidFriction`) plus a PMC surface with the additive `EmissiveMeshMaterial` from §C — but nobody has said so.

**8. Fog of war and minimap — the obvious implementation is blocked.** Standard fog-of-war is "render visibility into an RT, sample it in the terrain material". The terrain material is `VertexColorMaterial` or `VertexPaint_4Tex`, neither of which samples an arbitrary RT with world-space UVs, and you cannot author one that does. **The conventional implementation is closed.** The fallback is per-vertex: bake visibility into `FProcMeshVertex::Color` and push it through `UpdateMeshSection`. That is a materially different architecture and it must be decided **before the chunk vertex format is frozen** — and it collides directly with trap #23 (the sRGB create/update default mismatch). The *minimap* is easier and unblocked: `UCanvasRenderTarget2D` + a Slate `SImage` over the RT needs no material at all.

**9. Day/night and power systems.** A power grid (lamps going dark when a generator fails) is core to the genre and is the best consumer of §B's per-light `VolumetricScatteringIntensity` and `SetIntensity` findings — nobody connected them. No engine system is needed: it is a graph over your own tile data plus the renderer-side hooks already documented. For day/night, `Plugins/Experimental/DaySequence` exists (`IsExperimentalVersion: true`, Runtime + Editor modules) and is asset-driven — record it as a dead end and move on; it is arguably out of scope underground anyway.

**10. Task assignment and job scheduling — the actual AI problem.** §E answered *pathing* thoroughly and *behaviour authoring* honestly, then correctly identified job assignment as "a scheduling/auction problem over a task queue" — and dropped it. This is the central AI system of a mining game and it currently has no design and no engine anchor. Investigate `Source/Runtime/GameplayTasks` (`UGameplayTask`, `UGameplayTasksComponent`, `IGameplayTaskOwnerInterface`) — a Runtime engine module, no plugin, already transitive via `AIModule`, and completely unmentioned across all eight legs. It provides task lifecycle, priority and **resource locking** (two tasks cannot claim the same miner) without any asset. Also worth a look: `Plugins/Runtime/GameplayInteractions` and `Plugins/Runtime/GameplayBehaviorSmartObjects`, though both pull StateTree.

### P2 — cross-cutting concerns the brief asked about

**11. Memory budgets — entirely unaddressed.** The only datum anywhere in the corpus is §A's ~150 bytes/vertex with a permanent CPU copy per PMC section, and the recommended `UStaticMesh` migration adds a second copy. Nobody has computed a per-chunk budget or named a tool. Investigate `Source/Runtime/Core/Public/HAL/LowLevelMemTracker.h` (`LLM_SCOPE`, `DECLARE_LLM_MEMORY_STAT`, run with `-LLM`), `Plugins/Performance/MemoryUsageQueries`, `Plugins/WorldMetrics`, plus `stat memory`, `memreport -full` and `FPlatformMemory::GetStats()`.

**12. `GameplayDebugger` — the right debug system, missed.** §G found `ShaderPrint` (GPU-side) and §H found Slate; neither mentioned the gameplay-side framework, which is purpose-built for this: register a category, draw per-actor state on a key overlay, no asset, no UMG. `Source/Runtime/GameplayDebugger` — `GameplayDebuggerCategory.h`, `GameplayDebuggerAddonManager.h`. **Critically**, `Source/Runtime/GameplayDebugger/Public/GameplayDebugger.h:13-14` documents a two-tier compile: `WITH_GAMEPLAY_DEBUGGER` (full, absent in Shipping by default) versus `WITH_GAMEPLAY_DEBUGGER_CORE` (core only, you register categories yourself) — see `TargetRules.cs:431-436`. That distinction is exactly the silent-no-op class this project keeps hitting. Also `Plugins/Experimental/DrawDebugLibrary`.

**13. Iteration speed.** Hot-reload / Live Coding appears nowhere, despite §C noting `RecompileShaders Changed` for shaders only. A C++-only project with no assets lives or dies on C++ iteration time, and there are known Live Coding hazards directly relevant: §B's "set `ShadowCacheInvalidationBehavior` before `RegisterComponent`" and §G's `check()` on duplicate `AddShaderSourceDirectoryMapping` (which fires on a second `StartupModule`). Investigate UnrealBuildTool's Live Coding settings and `Source/Runtime/Core/Public/Misc/HotReloadInterface.h`. Also `Plugins/Experimental/SlateIM` (`IsExperimentalVersion: true`; modules `SlateIM`/`SlateIMEngine`/`SlateIMInGame`) — immediate-mode Slate, dramatically faster to iterate than retained `SCompoundWidget` for tuning panels, and a natural fit for a code-only project.

**14. Testing rendering outcomes.** §H found the automation framework and the correct headless command line, but not the harder problem: three separate legs independently found **silent no-op rendering failures** (PMC absent from the TLAS; HISM hardcoding `bVisibleInLumenScene = false`; VSM caching defeated by `bHasDeformableMesh`). Every one is invisible to a CPU-only test. Investigate `Source/Developer/ScreenShotComparison` + `Source/Developer/ScreenShotComparisonTools` for golden-image comparison, and `FAutomationScreenshotOptions` in `Source/Runtime/Engine/Classes/Engine/`. Combined with §G's `RenderCaptureInterface::FScopedCapture`, this is how the project gets a regression net around its most dangerous failure class.

## Configuration and code that is already correct — do not "fix" it

These were re-derived against the 5.8 tree and confirmed. Changing any of them will break something silently.

**`Config/DefaultEngine.ini`:**

- **SM6 must be *targeted*, not merely supported.** `+D3D12TargetedShaderFormats=PCD3D_SM6` **and** `-D3D12TargetedShaderFormats=PCD3D_SM5`. The engine picks the highest level from the targeted list; leaving SM5 in silently drops you to SM5 while every ray-tracing cvar still reads back `1`. This is the documented past failure and the reason for the boot gate in **Start here #2**.
- **`r.Lumen.HardwareRayTracing=1` is load-bearing, not a quality nicety.** Re-confirmed: no runtime-constructible geometry in 5.8 can satisfy the software branch of `UpdateVisibleInLumenScene`. Switching components does not fix this.
- **`r.Lumen.HardwareRayTracing.LightingMode=1` (hit lighting) is mandatory**, and is in fact the *only* option on a static-mesh-based pipeline: procedural geometry can never have Lumen surface cards, so surface-cache mode shades from nothing.
- **`r.SkinCache.CompileShaders=1` must be set before ray tracing is enabled**, or `RenderUtils.cpp` raises a Fatal log and hard-crashes on boot.
- **`r.DefaultFeature.AutoExposure` must stay `True`.** Setting it False disables the exposure feature entirely and the post-process Min/Max brightness are then ignored. Fixed exposure is achieved by leaving it on and pinning `Min == Max`. Note there is a *second* independent way to kill it: `r.EyeAdaptationQuality <= 0` clears `EngineShowFlags.EyeAdaptation` outright (`ShowFlags.cpp:483`). EV100 semantics also invert the pre-5.x intuition — **higher Min/Max = darker image**.
- **`r.Shadow.Virtual.Enable=1`** — the code default is 0. Your only shadow path for many local lights if MegaLights stays off.
- **`r.AllowStaticLighting=False`** — correct; there is nothing to bake and lights must be Movable for shadowed volumetric injection to work at all.
- **`r.MegaLights.EnableForProject=0`** — currently correct as a *default*, but this is now a genuine trade-off rather than a settled question. See §B before flipping it; the fog-injection consequence is real.
- **Volumetric fog** is the substrate for every god-ray in the game. Keep it.
- **No directional light and no sun.** Correct, and it is *why* screen-space light shafts are a dead end.

**`Source/DeepCore/Private/DeepCoreMaterials.cpp`:**

- The `#if WITH_EDITOR` guard around all `UMaterialEditorOnlyData` use (opens `:9`/`:25`, closes `:334`), with the non-editor fallback loading `/Engine/EngineDebugMaterials/VertexColorMaterial` and the comment "so a Game target still renders a recognisable world", is **exactly right**. It is what keeps DeepCore shippable as a cooked standalone build, and it is the evidence that closes the editor-linked-target question. Do not simplify it, and do not "unify the paths".

**`Source/DeepCore/DeepCore.Build.cs`:**

- `ProceduralMeshComponent` is correctly in `PublicDependencyModuleNames`, and it brings `RenderCore`, `RHI`, `MeshDescription`, `StaticMeshDescription` and `PhysicsCore` along publicly — several dependencies you might be tempted to add are already there.

**Standing verification rule:**

- **Verify by capturing a frame, never by reasoning.** This document contains at least three findings that were reasoned confidently and wrongly by an expert reading the same source (ISM angle-culling, MegaLights fog behaviour, and the `FCoreStyle` staging dead end), and caught only by a second pass. The rendering failure modes here are silent by construction. `r.Lumen.Visualize 3`, `r.RayTracing.Visualize`, `r.Shadow.Virtual.Visualize.ShowCachedPagesOnly`, `ProfileGPU`, and `p.Chaos.DebugDraw.Enabled 1` (Development builds only) are the instruments.
